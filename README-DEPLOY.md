# راهنمای استقرار دانیار روی VPS با DirectAdmin

این سند نحوه اجرای نهایی پلتفرم دانیار روی سرور مجازی (VPS) با پنل DirectAdmin را توضیح می‌دهد.

## ۱. پیش‌نیازها

- سرور با سیستم‌عامل لینوکس (Ubuntu/Debian/AlmaLinux)
- نصب Docker و Docker Compose:
  ```bash
  curl -fsSL https://get.docker.com | sh
  ```
- یک دامنه یا زیردامنه متصل به سرور (مثلاً `daniar.example.com`)
- در DirectAdmin دسترسی به بخش Custom HTTPD / Reverse Proxy یاSSL سایت

## ۲. دریافت پروژه و تنظیم متغیرها

```bash
cd /home/USERNAME/daniar    # مسیر دلخواه
cp .env.example .env
```

سپس در فایل `.env` مقادیر امن را بسازید (بدون این‌ها استقرار عمداً بالا نمی‌آید):

```bash
openssl rand -base64 32   # → SESSION_SECRET
openssl rand -base64 24   # → SOCKET_INTERNAL_SECRET
# → SUPERADMIN_INITIAL_PASSWORD (رمز اولیه مدیر کل — حداقل ۱۲ کاراکتر)
```

- هیچ کلید پیش‌فرضی در تصویر وجود ندارد؛ با کلید نمونه/فاقد، سرویس‌ها اجرا نمی‌شوند.
- رمز مدیر کل فقط برای «ساخت اولیه» استفاده می‌شود؛ اگر حساب مدیر کل از قبل وجود داشته باشد، رمز آن تغییر نمی‌کند.
- `DATABASE_URL` در سرور تنظیم نکنید — docker-compose خودش `file:/data/daniar.db` روی ولوم پایدار را ست می‌کند.
- کلیدهای اختیاری (VAPID، TURN، …) داخل `.env.example` توضیح داده شده‌اند.

## ۳. ساخت و اجرای کانتینر

```bash
bash scripts/deploy.sh    # پیش‌بررسی (Docker، کلیدها، آزاد بودن پورت 3034) + docker compose up -d --build
```

پشته شامل سرویس‌های زیر است:

| سرویس | نقش | انتشار روی میزبان |
|---|---|---|
| `init-data` | آماده‌سازی مالکیت ولوم برای کاربر غیر root (یک‌باره) | — |
| `migrate` | مهاجرت‌های ایمن Prisma (`migrate deploy` — هرگز داده حذف نمی‌کند) + مدیر کل اولیه | — |
| `web` | Next.js (کاربر غیر root، پورت 3000 داخلی) | — |
| `socket` | سرویس Socket.IO (کاربر غیر root، پورت 3003 داخلی) | — |
| `proxy` | تنها درگاه ورودی — Nginx داخلی | فقط `127.0.0.1:3034` |
| `livekit` | سرور رسانه SFU کلاس آنلاین (پروفایل `media` — بند ۷) | `7882/udp`، `7881/tcp` |
| `coturn` | TURN برای شبکه‌های محدود (پروفایل `turn` — اختیاری) | `3478/udp+tcp`، `5349/tcp+udp`، `49160-49200/udp` |

در اولین اجرا، سرویس migrate به‌صورت خودکار:

1. اگر دیتابیس از قبل وجود داشته باشد و جدول مهاجرت نداشته باشد، اول **تطابق واقعی schema** دیتابیس با زنجیره مهاجرت‌ها را با `prisma migrate diff` تأیید می‌کند (بازسازی وضعیت‌های پیشوندی و مقایسه) و فقط پس از تطابق، وضعیت پایه را ثبت و مهاجرت‌های pending را ایمن اعمال می‌کند (بدون `--accept-data-loss`). دیتابیس غیرمطابق = توقف کامل با حفظ داده‌ها (راه فرار آگاهانه: `DANIAR_BASELINE_FORCE=1`).
2. حساب **مدیر کل** را فقط اگر وجود نداشته باشد می‌سازد — رمز از `SUPERADMIN_INITIAL_PASSWORD` خوانده می‌شود و در هیچ لاگ/کدی ذخیره نمی‌شود.

`deploy.sh` و «موفقیت» اعلام می‌کند فقط پس از: ① پایان موفق سرویس migrate (کد خروج ۰) ② healthy‌شدن همه سرویس‌های فعال (web، socket، proxy و در صورت فعال‌بودن پروفایل‌ها livekit/coturn). در شکست، لاگ سرویس مشکل‌دار چاپ و با کد خطا خروج می‌شود. استقرار و به‌روزرسانی دو مسیر جدایند: استقرار اولیه = `scripts/deploy.sh`، نسخه جدید = `scripts/update.sh` (اگر stack موجود باشد deploy.sh به update.sh راهنمایی می‌کند).

بررسی وضعیت:

```bash
docker compose logs -f
docker compose ps
```

- سلامت واقعی سرویس‌ها با healthcheck سنجیده می‌شود (`/api/health` و `/healthz` — هر دو اتصال واقعی دیتابیس را می‌سنجند).
- درگاه ورودی فقط روی `127.0.0.1:3034` است؛ پورت‌های 80/443 و پنل DirectAdmin دست‌نخورده می‌مانند. قبل از اجرا، `scripts/deploy.sh` آزاد بودن پورت را بررسی می‌کند: اشغال توسط سرویس دیگر = خطای واضح بدون توقف آن سرویس؛ اشغال توسط stack موجود خود پروژه = مانع نیست (راهنمایی به update.sh).
- برای انتقال اولیه داده‌های موجود (دیتابیس + آپلودها): `bash scripts/import-data.sh db/custom.db uploads` — این اسکریپت اگر مقصد (ولوم) غیرخالی و دارای کاربر باشد، **متوقف می‌شود** تا داده‌های موجود حفظ شوند (`DANIAR_ALLOW_OVERWRITE=1` فقط با اطمینان کامل).
- محدودیت منابع (RAM/CPU/pids) و چرخش لاگ (json-file، ۱۰MB×۳) در `docker-compose.yml` تنظیم شده است.

## ۴. اتصال دامنه با Reverse Proxy در DirectAdmin

در DirectAdmin برای دامنه موردنظر یک **Reverse Proxy / Proxy Pass** تعریف کنید تا **تمام درخواست‌های دامنه — HTTP، WebSocket و آپلود —** به تنها درگاه پروژه یعنی `http://127.0.0.1:3034` هدایت شوند:

- قالب آماده Nginx: فایل `deploy/directadmin-nginx.conf` (در Custom HTTPD دامنه قرار دهید)
- قالب آماده Apache: فایل `deploy/directadmin-apache.conf` (ماژول‌های `proxy`، `proxy_http`، `proxy_wstunnel`، `headers` لازم است)

قالب‌ها شامل مسیرهای `/socket.io` و `/rtc` (سیگنالینگ کلاس آنلاین) و `/twirp` با upgrade WebSocket و مجموعه کامل هدرهای Host/Forwarded (ارسال با `$http_host` تا پورت حفظ شود)، `client_max_body_size 64m` برای آپلود ویدئو، و تایم‌اوت‌های بلند برای درخواست‌های طولانی (دستیار AI، ایمپورت اکسل) هستند.

⚠ قاعده ارث‌بری nginx: با تعریف حتی یک `proxy_set_header` داخل location، بقیه هدرهای سطح server در آن location بی‌اثر می‌شوند — به همین دلیل هدرهای Host/X-Forwarded-* داخل هر location تکرار شده‌اند (مسیرهای /socket.io و /rtc بدون این هدرها، Host به نام سرویس داخلی تبدیل و کوکی/سیگنالینگ خراب می‌شود).

- برای HTTPS، از بخش SSL در DirectAdmin گواهی **Let's Encrypt** صادر و «Force HTTPS» را فعال کنید.
- پراکسی باید هدر `X-Forwarded-Proto` را بفرستد (در قالب‌ها هست) تا کوکی‌های امن درست کار کنند.

## ۶. پشتیبان‌گیری و بازیابی و انتقال داده

```bash
bash scripts/backup.sh ./backups      # بکاپ آنلاین دیتابیس (integrity-check) + آپلودها
bash scripts/restore.sh backups/daniar-db-….db backups/daniar-uploads-….tar.gz
bash scripts/import-data.sh db/custom.db uploads   # انتقال اولیه داده‌های موجود به ولوم
```

- پشتیبان دیتابیس با `.backup` آنلاین SQLite انجام می‌شود (بدون توقف سرویس) و پیش از تحویل، `integrity_check` می‌گیرد.
- بازیابی **تراکنشی (همه‌یا‌هیچ)** است: اول همه اعتبارسنجی‌ها (یکپارچگی بکاپ + ۴ جدول حیاتی + اعتبارسنجی کامل آرشیو: مسیر مطلق/تراورسال، لینک/دستگاه/لوله، خارج از `uploads/`) انجام می‌شود و در خطای اعتبارسنجی **هیچ چیز — حتی سرویس‌ها — لمس نمی‌شود**. سپس سرویس‌ها متوقف و «محل بازگشت» داخل ولوم ساخته می‌شود (تصویر کامل دیتابیس فعلی db+wal+shm با checkpoint + انتقال rename-اتمیک آپلودها). جایگزینی فقط با «کپی → راستی‌آزمایی → rename اتمیک» انجام می‌شود؛ **در هر خطای میانی (جایگزینی، مهاجرت، سلامت سرویس‌ها) نسخه قبلی دیتابیس و آپلودها به‌صورت کامل بازگردانده و راستی‌آزمایی می‌شود** و در صورت شکست بازیابی، سرویس‌ها عمداً متوقف می‌مانند (با داده مشکوک روشن نمی‌شوند) با پیام واضح و دستور راه‌اندازی دستی. قفل هم‌زمانی جلوی دو بازیابی موازی را می‌گیرد. نسخه قبلی دیتابیس پس از موفقیت در `/data/daniar.db.prev` حفظ می‌شود و موفقیت فقط پس از مهاجرت موفق + healthy‌بودن همه سرویس‌های فعال اعلام می‌شود.
- گیت مهاجرت با `docker compose ps --all` بررسی می‌شود — موفقیت فقط وقتی اعلام می‌شود که کانتینر migrate واقعاً پایان یافته و کد خروجش صفر باشد (کانتینرِ در حال اجرا هرگز «موفق» شمرده نمی‌شود).
- کل داده‌های پلتفرم (دیتابیس + پیوست‌ها) در ولوم `daniar_data` است؛ به‌روزرسانی/بازسازی کانتینرها هرگز ولوم را حذف نمی‌کند.

## ۶. پیام‌رسان بلادرنگ (Socket.IO) — مسیر درگاه

پیام‌رسان از یک سرویس مستقل Socket.IO داخل شبکه داخلی Docker (پورت 3003) استفاده می‌کند. کلاینت همان دامنه سایت را صدا می‌زند (`/socket.io/...`)؛ درگاه داخلی `proxy` این مسیر را به سرویس سوکت می‌فرستد و پراکسی DirectAdmin فقط کل ترافیک دامنه را به `127.0.0.1:3034` می‌فرستد (قالب‌های بخش ۴).

نکته‌ها:
- متغیرهای `NEXT_PUBLIC_SOCKET_URL=/` و `NEXT_PUBLIC_SOCKET_PATH=/socket.io` هنگام build به‌صورت build-args تنظیم می‌شوند — دست نزنید.
- `SOCKET_INTERNAL_SECRET` را با `openssl rand -base64 24` بسازید (الزامی؛ بدون آن سرویس‌ها اجرا نمی‌شوند).
- ارتباط داخلی Next.js ← Socket با متغیر `SOCKET_INTERNAL_URL=http://socket:3003` روی شبکه داخلی است و هیچ پورتی از سوکت/وب روی میزبان منتشر نمی‌شود.
- فایل‌های پیوست روی ولوم `/data/uploads` ذخیره می‌شوند و محدودیت حجم دارند (تصویر ۸MB، ویدئو ۵۰MB، صوت ۲۰MB، فایل ۲۰MB).

## ۷. کلاس آنلاین صوتی و تصویری — SFU با LiveKit

معماری رسانه: **SFU (Selective Forwarding Unit) با LiveKit** — هر شرکت‌کننده رسانه‌اش را یک‌بار به سرور رسانه می‌فرستد و سرور آن را برای بقیه بازپخش می‌کند. این معماری برخلاف mesh قدیم، با تعداد زیاد کلاس هم‌زمان و کلاس‌های ۳۰-۴۰ نفره هم مقیاس‌پذیر است و ترافیک آپلود هر ناشر فقط یک‌بار است.

**جداسازی سرویس‌ها (الزام طراحی):**
- سرویس رسانه (LiveKit) **مستقل از Next.js و Socket.IO** اجرا می‌شود — فشار کلاس‌های آنلاین هرگز پیام‌رسان، تکالیف، حضور و غیاب و OTP را مختل نمی‌کند.
- هر جلسه یک **اتاق مستقل LiveKit** با نام `live:{sessionId}` دارد؛ جداسازی کامل کاربران و رسانه بین جلسه‌ها + حذف خودکار اتاق پس از پایان جلسه.
- کلاینت‌ها فقط توکن کوتاه‌عمر می‌گیرند؛ **توکن فقط در سرور** و فقط پس از احراز هویت + فعال‌بودن امکان کلاس آنلاین + بررسی عضویت واقعی کلاس + استعلام «اخراج‌نشده» از سرویس جلسه صادر می‌شود.
- مجوز رسانه در توکن متناسب با نقش است: معلم/مدیر = انتشار صدا/دوربین/صفحه؛ دانش‌آموز = فقط دریافت. **گیت انتشار دانش‌آموز در خود سرور رسانه هم اعمال می‌شود**: اجازه‌های بعدی معلم (صحبت/دوربین/اشتراک) با RoomService به LiveKit اعمال می‌شود و لغو اجازه، ترک منتشرشده را در سرور رسانه نیز ساکت/حذف می‌کند. روشن‌شدن رسانه دانش‌آموز علاوه بر اجازه معلم، همیشه نیازمند اقدام خود اوست.
- سیگنالینگ LiveKit از مسیر `/rtc` همان درگاه 3034 و SSL دامنه می‌گذرد — **پورت‌ها و تنظیمات DirectAdmin تغییر نمی‌کند**.

**پورت‌های لازم (جدا از درگاه 3034):**

| پورت | پروتکل | کاربرد | الزامی؟ |
|---|---|---|---|
| `127.0.0.1:3034` | TCP | تنها درگاه وب (صفحات، API، `/socket.io`، `/rtc`) | بله — مثل قبل |
| `7882` | UDP | رسانه WebRTC به SFU (مسیر اصلی) | بله |
| `7881` | TCP | فالبک رسانه وقتی UDP بسته است | توصیه‌شده |
| `3478` UDP+TCP | TURN/STUN | شبکه‌های محدود (پروفایل `turn`) | اختیاری |
| `5349` TCP+UDP | TURN over TLS/DTLS | شبکه‌هایی که فقط 443 را باز می‌گذارند (نیازمند گواهی) | اختیاری |
| `49160-49200` UDP | رله TURN | سقف جلسات هم‌زمانِ رله‌شده | اختیاری |

**فرض‌های برآورد (شفاف — پارامترهای واقعی کد):**

| مورد | مقدار | توضیح |
|---|---|---|
| ویدیوی ناشر (معلم) | 720p@15fps — `maxBitrate 700kbps` | simulcast سه‌لایه (~150/300/700) |
| اشتراک صفحه | `maxBitrate 1.2Mbps@8fps` | contentHint=detail برای متن تخته |
| صدا | Opus با DTX (~20-40kbps واقعی) | echoCancellation/noiseSuppression روشن |
| مصرف هر دانش‌آموز (دریافت) | ~750kbps کامل / ~250kbps حالت کم‌مصرف | ویدیوی معلم + صدا |
| حالت کم‌مصرف | کیفیت لایه LOW روی دوربین و اشتراک صفحه | دکمه در نوار کنترل؛ ماندگار بین جلسه‌ها |
| کیفیت تطبیقی | `adaptiveStream + dynacast` | سرور کیفیت را با اندازه پنجره/ازدحام تنظیم می‌کند |
| ناشران هم‌زمان هر جلسه | ۱ معلم + دانش‌آموزانِ دارای اجازه (پیشنهاد ≤۴) | سقف سخت: `LIVE_MAX_PARTICIPANTS` (پیش‌فرض ۳۲؛ ظرفیت اختصاصی هر کلاس از پنل مدیر کل) |
| سرفصل هر جلسه | آپلود معلم ~750kbps + دانلود هر بیننده ~750kbps | در SFU آپلود مستقل از تعداد بیننده است |
| ظرفیت سرور (حدس مهندسی، نه تضمین) | 4vCPU/8GB ≈ ۳۰-۴۰ کلاس هم‌زمانِ ۱۰ نفره | دانلود کل ≈ کلاس‌ها × ۹ × 750kbps ≈ 270-340Mbps؛ 1GB RAM ≈ ۱۰۰ شرکت‌کننده هم‌زمان LiveKit |
| باند LAN سرور | 1Gbps ≈ سقف عملی ~۶۰-۷۰ کلاس ۱۰ نفره | قبل از CPU اشباع می‌شود |

این اعداد بر اساس انکودرهای ثابت کد هستند؛ مقیاس واقعی به شبکه سرور و شبکه دانش‌آموزان بستگی دارد و باید با آزمون میدانی تأیید شود.

**فرمان اجرای LiveKit و سازگاری ایمیج (مهم):** ایمیج پین‌شده `livekit/livekit-server:v1.13.9` دارای `ENTRYPOINT = ["/livekit-server"]` است — اگر به‌جای آرگومان، فرمان shell بدهیم، باینری با «flag provided but not defined» کرش‌لوپ می‌شود (همین باعث قطعی استریم شد). compose اکنون `entrypoint` را به sh ایمیج بازنویسی و باینری را با مسیر مطلق exec می‌کند (تست‌شده). IP عمومی با فلگ بومی `--node-ip` از `LIVEKIT_NODE_IP` پاس می‌شود؛ `use_external_ip: false` است تا استارت سرور به STUN خارجی وابسته نباشد — در شبکه‌های محدود، تکیه بر STUN به «could not resolve external IP» و کرش می‌رسید.

**TURN برای شبکه‌های محدود (جایگزین SFU نیست):**
- TURN فقط مسیر اضطراری رسانه برای شبکه‌هایی است که UDP به 7882 را می‌بندند؛ همه رسانه همچنان از SFU می‌گذرد و TURN فقط ترافیک را به سرور رسانه رله می‌کند.
- با پروفایل `turn` (در `.env`: `COMPOSE_PROFILES=media,turn`) سرویس coturn با اعتبارنامه `LIVE_TURN_USERNAME/LIVE_TURN_CREDENTIAL` بالا می‌آید؛ این متغیرها داخل environment سرویس coturn تعریف شده‌اند و همان مقادیر در STUN/TURN کلاینت‌ها (پاسخ توکن) استفاده می‌شوند. (تگ ایمیج `coturn/coturn:4.18-alpine` است — تگ 4.6-alpine در رجیستری وجود ندارد.)
- IP عمومی VPS هم برای LiveKit (`LIVEKIT_NODE_IP`، الزامی با پروفایل media) و هم برای TURN (`TURN_EXTERNAL_IP`، الزامی با پروفایل turn) در `.env` تنظیم می‌شود و `deploy.sh` هر دو را اعتبارسنجی می‌کند.
- TLS اختیاری TURN: گواهی/کلید را در `deploy/coturn/` بگذارید و `TURN_CERT_FILE=/etc/coturn/cert.pem` و `TURN_KEY_FILE=/etc/coturn/key.pem` را در `.env` تنظیم کنید؛ بدون گواهی سرویس با `--no-tls --no-dtls` روی 3478 کار می‌کند.
- رله هر جلسه‌ی ۱۰ نفره تا ~7Mbps مصرف می‌کند — بازه ۴۱ پورت رله برای ده‌ها کلاس کافی است.

**سرور رسانه جدا:** در `.env` مقدار `COMPOSE_PROFILES` را خالی کنید (LiveKit محلی بالا نمی‌آید)، `NEXT_PUBLIC_LIVEKIT_WS_URL=wss://live.example.com` (دامنه/SSL جدا برای مرورگرها) و `LIVEKIT_INTERNAL_URL` (آدرس مدیریتی از سمت سرورهای web/socket) را به سرور رسانه بدهید و همان `LIVEKIT_API_KEY/SECRET` را آنجا تنظیم کنید. هیچ تغییر دیگری لازم نیست.

**پیکربندی (docker-compose / env):**
```
COMPOSE_PROFILES=media           # LiveKit روی همین سرور (پیش‌فرض .env.example)
LIVEKIT_API_KEY=...              # openssl rand -hex 16
LIVEKIT_API_SECRET=...           # openssl rand -base64 32 (حداقل ۳۲ کاراکتر — الزام خود LiveKit)
LIVEKIT_NODE_IP=<PUBLIC_IP>      # IP عمومی VPS — الزامی با پروفایل media
LIVE_MAX_PARTICIPANTS=32         # سقف سراسری هر جلسه (پیش‌فرض ۳۲؛ ظرفیت اختصاصی هر کلاس از پنل مدیر کل)
LIVE_STUN_URLS=stun:stun.l.google.com:19302
# اختیاری — TURN:
# COMPOSE_PROFILES=media,turn
# LIVE_TURN_URLS=turn:<PUBLIC_IP>:3478
# LIVE_TURN_USERNAME=...   LIVE_TURN_CREDENTIAL=...
# TURN_EXTERNAL_IP=<PUBLIC_IP>   (الزامی با پروفایل turn)
```

**نیازهای شبکه:**
- HTTPS الزامی است (getUserMedia فقط روی HTTPS یا localhost کار می‌کند).
- signaling همان مسیر `/rtc` درگاه 3034 را استفاده می‌کند؛ رسانه مستقیم به `7882/udp` سرور می‌رود — این پورت باید از اینترنت قابل دسترس باشد (روی میزبان منتشر می‌شود، نه از داخل DirectAdmin).

**اجازه‌ها:** روشن‌شدن میکروفون/دوربین همیشه با اقدام خود کاربر است؛ معلم فقط می‌تواند محدود کند (سکوت اجباری، قطع اجازه صحبت/اشتراک/دوربین) و هرگز نمی‌تواند از راه دور دستگاه دانش‌آموز را روشن کند. برای یک کلاس فقط یک جلسه فعال مجاز است و دسترسی ورود (معلم منتسب، دانش‌آموز همان کلاس، مدیر همان مدرسه) کامل سمت سرور بررسی می‌شود.

## ۸. دستیار هوش مصنوعی «دستیار دانیار»

گفتگوی اختصاصی هوش مصنوعی برای نقش **مدیر مدرسه** در فهرست گفتگوها. تمام پیکربندی از پنل مدیر کل (منوی «دستیار هوش مصنوعی» در `/admin/ai`) انجام می‌شود و نیازی به متغیر محیطی اجباری ندارد.

**پیکربندی سرویس (سمت مدیر کل):**
- ارائه‌دهنده: `openai` (سازگار با endpoints متوافق) یا `anthropic` + امکان درج **Base URL** برای دروگاه‌های شرکتی یا سرویس‌های سازگار
- مدل و کلید API — کلید فقط در دیتابیس سمت سرور نگهداری می‌شود، در هیچ پاسخ API، لاگ یا متن خطایی نمایش داده نمی‌شود (فقط ۴ رقم آخر ماسک‌شده)
- دکمه «آزمایش اتصال» یک درخواست واقعی به سرویس می‌زند و نتیجه واقعی (تأخیر، پاسخ کوتاه مدل یا خطای واقعی سرویس‌دهنده) را نشان می‌دهد؛ هیچ پاسخ ساختگی تولید نمی‌شود
- دستورالعمل عمومی + دستورالعمل نقش مدیر مدرسه، و سقف «بیشینه دور ابزار» برای کنترل هزینه

**فعال‌سازی و سهمیه:** دستیار برای هر مدرسه جداگانه فعال/غیرفعال می‌شود (به‌همراه کلید نقش مدیر مدرسه) و «سهمیه پیام روزانه هر کاربر» اختیاری دارد. همه این گیت‌ها علاوه بر رابط، سمت سرور نیز اعمال می‌شوند.

**امنیت داده:**
- ابزارهای دستیار (`school_overview`، `list_classes`، `assignment_status`، `list_students`، `student_detail`) شناسه مدرسه را فقط از نشست کاربر می‌گیرند؛ مدل هرگز نمی‌تواند به مدرسه دیگری کوئری بزند و کل دیتابیس یا تاریخچه گروه‌ها به مدل فرستاده نمی‌شود
- پاسخی که از داده برنامه ساخته شده، منابع واقعی خود (تکلیف/کلاس/گروه/دانش‌آموز) را به‌صورت چیپ «بر اساس این داده‌ها» نمایش می‌دهد
- آمار مدیر کل فقط شمارنده مصرف/خطاست؛ متن گفتگوهای خصوصی کاربران برای مدیر کل قابل مشاهده نیست
- تاریخچه گفتگوها دائمی و خصوصی هر کاربر است؛ حذف گفتگو با تأیید دو مرحله‌ای انجام می‌شود

**متغیر محیطی اختیاری:** `AI_TIMEOUT_MS` (پیش‌فرض ۱۲۰۰۰۰) — مهلت هر فراخوانی سرویس.

**نکته شبکه:** اگر منطقه سرور توسط OpenAI/Anthropic محدود شده باشد، خطای واقعی سرویس‌دهنده در «آزمایش اتصال» نمایش داده می‌شود؛ در این حالت از یک دروگاه سازگار با Base URL استفاده کنید. سرور `scripts/ai-test-server.mjs` (پورت 3055) فقط زیرساخت آزمون توسعه است و نباید در محیط عملیاتی استفاده شود.

## ۹. ورود پیامکی (کد یک‌بارمصرف) و اعلان‌ها

**ورود پیامکی** فقط برای کاربران عادی (مدیر مدرسه/معلم/دانش‌آموز) است؛ مدیر کل همیشه با رمز از `/superadmin` وارد می‌شود. پیکربندی کامل در پنل مدیر کل → منوی «ورود پیامکی» (`/admin/sms`).

**سرویس‌های پیامکی پشتیبانی‌شده (هر کدام مطابق مستندات خودش):**
- **SMS.ir** — متد «ارسال کد تایید» (`POST /v1/send/verify` با هدر `x-api-key` و قالب TemplateId که متغیر `CODE` دارد)
- **ملی پیامک** — سرویس OTP پنل (`rest.payamak-panel.com/api/SendOTP/SendOTP`) با نام کاربری/رمز پنل و خط خدماتی
- **فراز اس‌ام‌اس** — ارسال با قالب Pattern از `api2.ippanel.com` با هدر `apikey`
- **OTPy** — مستندات رسمی این سرویس در دسترس این پیاده‌سازی نبود؛ به‌جای اتصال ساختگی، حالت «REST سازگار» ارائه شده است که آدرس، هدر احراز هویت و بدنه JSON (با متغیرهای `{{phone}}` و `{{code}}`) را طبق مستندات خود سرویس‌دهنده وارد می‌کنید و درخواست واقعاً به همان آدرس ارسال می‌شود

**امنیت:**
- کد یک‌بارمصرف فقط به‌صورت هش (SHA-256 + HMAC شماره) ذخیره می‌شود؛ در دیتابیس، لاگ یا گزارش هرگز خام نیست
- شماره تلفن در گزارش‌ها ماسک می‌شود (`0912***6789`)؛ گزارش‌ها کد ورود و کلید سرویس ندارند
- اعتبارهای سرویس فقط سمت سرور؛ در پاسخ API فقط ماسک نمایش داده می‌شود
- محدودیت‌ها سمت سرور: انقضای کد (پیش‌فرض ۱۲۰ ثانیه)، فاصله ارسال مجدد (۶۰ ثانیه با شمارش معکوس)، سقف تلاش برای هر کد (۵ بار)، سقف درخواست ساعتانه برای هر شماره و محدودت IP
- پاسخ درخواست کد عمومی است و وجود یا نبودِ حساب را افشا نمی‌کند؛ حساب/مدرسه غیرفعال پیامکی نمی‌گیرد و وارد نمی‌شود

**شماره تلفن:** در کل پلتفرم یکتاست؛ نرمال‌سازی ارقام فارسی/انگلیسی و قالب‌های `۰۹/۹۸/+۹۸/۰۰۹۸` به قالب واحد `09xxxxxxxxx`. تغییر شماره عملیات حساس است و فقط مدیر مدرسه برای کاربران مدرسه خودش (با تأیید رمز عبور خودش در سربرگ ویرایش کاربر) انجام می‌شود. کاربر بدون شماره همچنان با نام کاربری/رمز وارد می‌شود.

**اعلان‌ها:** پیام خصوصی، پیام گروهی، تکلیف جدید، بازخورد معلم، دعوت کلاس آنلاین و اطلاعیه مدرسه — هر رویداد دقیقاً یک‌بار برای هر کاربر ثبت می‌شود (کلید ضدتکرار)؛ پیام خودکارِ تکلیف/جلسه اعلان تکراری نمی‌سازد. بی‌صدایی هر گفتگو از سربرگ گفتگو یا تنظیمات، اعلان آن گفتگو را قطع می‌کند (اطلاعیه رسمی مستثناست). اعلان مرورگر فقط با رضایت کاربر فعال می‌شود؛ بدون پیش‌نمایش، هیچ متن حساسی روی صفحه قفل نمایش داده نمی‌شود.

**PWA:** وب‌اپ با `manifest.webmanifest` و آیکون‌ها قابل نصب است؛ Service Worker فقط فایل‌های ایستا را کش می‌کند و پاسخ API/صفحات خصوصی هرگز کش نمی‌شوند. خروج از حساب کش و storage مرورگر را پاک می‌کند تا اطلاعات حساب قبلی برای کاربر بعدی نمایش داده نشود.

## ۱۰. حضور و غیاب تقویم‌محور (مرحله ۸)

بخش مستقل «حضور و غیاب» در منوی موبایل و دسکتاپ — کاملاً بر پایه تقویم جلالی ایرانی (هفته از شنبه، ماه‌های فارسی):

- **ساختار**: هر فهرست حضور و غیاب متعلق به یک کلاس + یک روز جلالی + یک جلسه مشخص است و به گروه درسی وابسته نیست. جلسه دو وضعیت دارد: «پیش‌نویس» و «نهایی».
- **معلم**: فقط برای کلاس‌های مجاز خودش (انتساب واقعی به گروه‌ها) — انتخاب روز در تقویم، انتخاب کلاس، همه دانش‌آموزان پیش‌فرض «حاضر» با چک‌باکس، یادداشت غیبت اختیاری، سوابق جلسات خودش و اصلاح با حفظ کامل سابقه (`AttendanceEditLog`).
- **دانش‌آموز**: «حضور و غیاب من» — فقط سوابق نهایی‌شده خودش با تقویم و آمار؛ هیچ توان تغییر یا دیدن سایرین ندارد (سمت سرور هم اعمال می‌شود؛ ۴۰۴).
- **مدیر مدرسه**: گزارش کل مدرسه با فیلتر کلاس/معلم(ثبت‌کننده)/دانش‌آموز/بازه تاریخ جلالی/وضعیت، آمار هر دانش‌آموز و کلاس، اصلاح وضعیت‌ها و خروجی اکسل سه‌شیتی راست‌به‌چپ (`GET /api/attendance/report/export`).
- **گزارش**: «ثبت‌نشده» (دانش‌آموز ثبت‌نام‌شده بدون رکورد در جلسه نهایی‌شده) جدا نمایش داده می‌شود و غیبت حساب نمی‌شود؛ جلسات پیش‌نویس در آمار محاسبه نمی‌شوند.
- **اعلان**: پس از نهایی‌سازی برای هر دانش‌آموز اعلان خصوصی (کلید ضدتکرار `att-final:{session}:{student}` — هرگز تکراری نمی‌شود)؛ تغییر وضعیت بعدی → اعلان اصلاح (`ATTENDANCE_CORRECTION` با شماره اصلاح). هیچ اطلاعاتی در گروه عمومی منتشر نمی‌شود.
- **امکانات مدرسه**: کلید `attendance` در پرچم‌های هر مدرسه (پیش‌فرض فعال؛ از پنل مدیر کل قابل خاموش‌کردن است و همه مسیرها گیت می‌شوند).

## ۱۱. کتابخانه نمونه‌سؤالات (مرحله ۹)

بخش مستقل «نمونه‌سؤالات» در منوی موبایل و دسکتاپ — کتابخانه انتشار و دریافت نمونه‌سؤال:

- **ساختار**: هر نمونه‌سؤال متعلق به کلاس‌های انتخاب‌شده معلم است (چندکلاسه با `SampleQuestionClass`) و به گروه درسی وابسته نیست. نام درس برای دسته‌بندی و جست‌وجو، و موضوع به‌صورت اختیاری ثبت می‌شود. وضعیت انتشار: «منتشرشده» یا «پیش‌نویس» (دانش‌آموز فقط منتشرشده را می‌بیند).
- **معلم**: فقط برای کلاس‌های مجاز خودش (انتساب واقعی به گروه‌ها) — عنوان، نام درس، موضوع، توضیح، چند فایل سؤال و چند فایل پاسخ‌نامه (PDF، تصویر و Word رایج؛ اعتبارسنجی نوع و حجم سمت سرور، حداکثر ۲۰ مگابایت برای هر فایل)، کلید فعال/غیرفعال نمایش پاسخ‌نامه، ویرایش نمونه‌سؤال خودش با حفظ امن فایل‌ها (جایگزینی/حذف هر فایل فقط کلید یکتای همان نمونه‌سؤال را حذف می‌کند و هرگز فایل نمونه‌سؤال دیگری را).
- **ارسال پیام به گروه**: هنگام انتشار، معلم می‌تواند پیام خودکار با دکمه «مشاهده نمونه‌سؤال» در یکی از گروه‌های درسی کلاس‌های مخاطب بفرستد (کارت `SAMPLEQ` در چت). تلاش مجدد هرگز پیام یا نمونه‌سؤال تکراری نمی‌سازد (`clientId` یکتا روی نمونه‌سؤال + `clientId` قطعی `sampleq-announce:{qid}:{groupId}` روی پیام).
- **دانش‌آموز**: نمونه‌سؤالات منتشرشده کلاس خودش با جست‌وجوی عنوان/درس/موضوع، فیلتر درس، نشان‌گذاری «فقط نشان‌دارها» (تخصیصی هر دانش‌آموز با `SampleQuestionBookmark`)، جزئیات با نام معلم و تاریخ انتشار، دانلود با احراز هویت و پیش‌نمایش PDF و تصویر؛ پاسخ‌نامه فقط در صورت فعال‌بودن نمایش (در غیر این صورت ۴۰۴ حتی با دانستن شناسه فایل).
- **مدیر مدرسه**: همه نمونه‌سؤالات مدرسه با فیلتر کلاس/درس/معلم/وضعیت انتشار، مشاهده مخاطبان (فهرست دانش‌آموزان هر کلاس) و فایل‌ها، لغو انتشار و حذف. مدیر مدرسه دیگر حتی با دانستن شناسه، ۴۰۴ می‌گیرد.
- **اعلان**: انتشار برای همه دانش‌آموزان فعال کلاس‌های مخاطب اعلان خصوصی می‌سازد (کلید ضدتکرار `sampleq:{qid}` — انتشار مجدد هرگز اعلان تکراری نمی‌سازد؛ افزودن کلاس جدید و انتشار دوباره فقط به دانش‌آموزان بدون اعلان قبلی می‌رسد) و پیام خودکار گروهی اعلان جداگانه `GROUP_MESSAGE` ندارد (بدون اعلان دوتایی). کلیک اعلان صفحه همان نمونه‌سؤال را باز می‌کند.
- **دسترسی سمت سرور**: همه دانلودها از `/api/sample-questions/{id}/files/{fileId}` با نشست معتبر و بررسی نقش/عضویت کلاس/مدرسه سرو می‌شوند؛ تغییر شناسه نمونه‌سؤال، کلاس یا فایل دسترسی بین‌مدرسه‌ای نمی‌سازد.
- **امکانات مدرسه**: کلید `sampleq` در پرچم‌های هر مدرسه (پیش‌فرض فعال؛ از پنل مدیر کل قابل خاموش‌کردن است).

## ۱۲. پوش نوتیفیکیشن واقعی مرورگر (Web Push)

اعلان‌های مرورگر دانیار با **Web Push + Service Worker** پیاده‌سازی شده‌اند تا حتی وقتی صفحه برنامه باز نیست هم دریافت شوند. این سیستم با اعلان‌های درون‌برنامه‌ای یکپارچه است (نه موازی نه تکراری): هر رویداد یک‌بار در دیتابیس ثبت می‌شود و پوش از روی همان ردیف اعلان با شناسه یکتا ارسال می‌گردد.

### الف) کلیدهای VAPID (الزامی برای فعال‌شدن پوش)

```bash
bunx web-push generate-vapid-keys
```

خروجی دو کلید می‌دهد؛ در `.env` سرور (خارج از مخزن) قرار دهید:

```env
VAPID_PUBLIC_KEY=...          # کلید عمومی — به مرورگر می‌رود
VAPID_PRIVATE_KEY=...         # کلید خصوصی — فقط همین‌جا؛ هرگز در کد/مخزن/لاگ نمی‌رود
VAPID_SUBJECT=mailto:admin@example.com
```

- اگر کلیدها را عوض کنید همه اشتراک‌های موجود باطل می‌شوند — پس **در هر راه‌اندازی مجدد ثابت بمانند** (`.env.example` نمونه بدون کلید واقعی است).
- کلید خصوصی فقط سمت سرور خوانده می‌شود (`src/lib/push.ts`)؛ به مرورگر، لاگ یا پاسخ API نمی‌رود.
- بدون این کلیدها بقیه برنامه کار می‌کند؛ فقط پوش غیرفعال می‌ماند و وضعیت آن در «اعلان‌ها → پیکربندی» پنل مدیر کل شفاف نشان داده می‌شود.

### ب) نیازهای شبکه

ارسال پوش از سرور به سرویس‌های پوش مرورگرها نیازمند **دسترسی خروجی HTTPS** است:

| مرورگر | سرویس مقصد |
|---|---|
| Chrome / Edge / Opera | `fcm.googleapis.com` (پورت 443) |
| Firefox | `autoupdate.push.services.mozilla.com` (پورت 443) |
| Safari (macOS/iOS) | سرویس Apple Push |

اگر فایروال خروجی دارید، این دامنه‌ها را باز کنید. قطعی دسترسی خروجی، ارسال‌ها را ناموفق می‌کند ولی هیچ‌گاه ثبت پیام/تکلیف را شکست نمی‌دهد (صف با تلاش مجدد محدود و انقضای زمانی ادامه می‌دهد).

### ج) استقرار پشت DirectAdmin و Docker

- پوش فقط روی **HTTPS دامنه اصلی** کار می‌کند (نیازمندی مرورگرها). Reverse Proxy نیازی به تنظیم اضافه ندارد؛ مسیر `/sw.js` از خود Next سرو می‌شود.
- Service Worker در مسیر `/sw.js` با scope `/` است و با Service Worker PWA قبلی همان فایل یکپارچه شده است (کش فقط فایل‌های ایستا؛ API و صفحات خصوصی هرگز کش نمی‌شوند).
- متغیرهای env باید به کانتینر برسند (`docker-compose.yml` بخش environment یا فایل env خارجی).

### د) مدیریت و کلیدها

- **پنل مدیر کل ← «اعلان‌ها»**: کلید پلتفرم (روشن/خاموش کل پوش)، کلید پوش هر مدرسه، وضعیت VAPID، آمار موفق/ناموفق و خطاهای عمومی (بدون هیچ محتوای خصوصی، endpoint یا کلید).
- **پنل مدیر مدرسه ← «اعلان‌ها»**: وضعیت مدرسه + راه‌های ایجاد اعلان (اطلاعیه، تکلیف، جلسه، نمونه‌سؤال، حضور و غیاب) + فعال‌سازی دستگاه خودش.
- **تنظیمات هر کاربر** (`/settings`): فعال/غیرفعال‌کردن پوش همین دستگاه با توضیح قبلی (درخواست مجوز مرورگر فقط با کلیک کاربر)، انتخاب نوع رویدادها، پیش‌نمایش متن پیام (پیش‌فرض خاموش)، بی‌صدایی گفتگوها، فهرست دستگاه‌ها و لغو اشتراک، و دکمه «ارسال اعلان آزمایشی به این دستگاه» با نتیجه واقعی ارسال.
- تنظیم دقیق صف: `PUSH_RETRY_BASE_SECONDS` (پیش‌فرض ۴۵)، `PUSH_MAX_ATTEMPTS` (پیش‌فرض ۳)، `PUSH_TTL_MINUTES` (پیش‌فرض ۱۵ — اعلان‌های قدیمی‌تر ارسال نمی‌شوند).

### هـ) محدودیت‌های واقعی مرورگر/سیستم‌عامل (شفاف به کاربر نمایش داده می‌شود)

| محیط | وضعیت پوش |
|---|---|
| Chrome/Edge/Firefox دسکتاپ و اندروید | ✅ کامل (روی HTTPS) |
| Safari macOS 16.4+ | ✅ کامل |
| iOS/iPadOS 16.4+ | ⚠ فقط برای **وب‌اپ نصب‌شده** (Add to Home Screen) — برنامه راهنمای نصب نشان می‌دهد |
| iOS قدیمی‌تر از ۱۶٫۴ | ❌ پشتیبانی نمی‌شود (اپ برنامه را پشتیبانی‌نشده نشان می‌دهد) |
| حالت مجوز «مسدود» | راهنمای فعال‌سازی از تنظیمات مرورگر نمایش داده می‌شود و درخواست مجوز تکرار نمی‌شود |
| حالت صرفه‌جویی باتری، Focus/Do Not Disturb، بسته‌بودن مرورگر | ممکن است اعلان متوقف/به‌تأخیر بیفتد — تضمین تحویل وجود ندارد |

برنامه قابلیت را از خود دستگاه تشخیص می‌دهد (`PushManager`/`Service Worker`/HTTPS/نصب PWA) و وضعیت دقیق «فعال، غیرفعال، مسدودشده یا پشتیبانی‌نشده» را نشان می‌دهد.

## ۱۳. مدیریت کاربران: افزودن تکی/گروهی، ایمپورت اکسل، کدملی و رمز پیش‌فرض

سیستم افزودن کاربر برای هر دو پنل (مدیر مدرسه در `/modir/users` و مدیر کل در `/admin/users`) بازطراحی شده است.

### الف) قواعد مشترک همه مسیرهای ایجاد کاربر

- **فیلدهای افزودن کاربر**: نام، نام خانوادگی، نقش، کدملی، شماره تماس (اختیاری)، کلاس (فقط دانش‌آموز). مدیر کل فیلد «مدرسه» را هم دارد.
- **نام کاربری همه کاربران = کدملی** (فقط عدد؛ ارقام فارسی خودکار تبدیل می‌شود؛ یکتا در کل پلتفرم).
- **رمز عبور اولیه همه کاربران = `123456`** — هیچ فیلد رمز در فرم‌های افزودن نیست؛ کاربر/مدیر بعداً می‌تواند تغییرش دهد.
- **رمز ضعیف مجاز است**: حداقل ۶ کاراکتر، «فقط عدد» یا «فقط حرف» پذیرفته می‌شود (سقف ۷۲ کاراکتر = محدودیت bcrypt). این قانون روی همه مسیرهای تغییر رمز (تنظیمات کاربر، تغییر رمز توسط مدیر، ایمپورت) یکسان اعمال می‌شود.
- کلاس فقط برای دانش‌آموز اعمال می‌شود (ثبت‌نام کلاسی خودکار)؛ معلم و مدیر مدرسه کلاس نمی‌گیرند.

### ب) سه راه افزودن

1. **افزودن گروهی دانش‌آموزان** (بالای صفحه، آکاردئونی): لیست خالیِ قابل گسترش — با «افزودن ردیف» پر می‌شود و با یک کلیک «ثبت کل لیست» همه در کلاس انتخابی ثبت‌نام می‌شوند. نتیجه هر ردیف (موفق/خطا با دلیل) نمایش داده می‌شود؛ ردیف خطادار بقیه را متوقف نمی‌کند.
2. **افزودن کاربر تکی**: فرم با همان فیلدها؛ نقش در پنل مدیر کل شامل «مدیر مدرسه» هم هست.
3. **ایمپورت فایل اکسل (xlsx/xls/csv)**: ستون‌های «نام، نام خانوادگی، نقش، کدملی، شماره همراه». **انتخاب کلاس قبل از آپلود الزامی است** (دکمه بارگذاری تا کلاس انتخاب نشود غیرفعال است). دکمه «دانلود فایل اکسل نمونه» قالب استاندارد می‌دهد. نقش خالی = دانش‌آموز؛ نقش فارسی یا انگلیسی پذیرفته می‌شود. پیش‌نمایش اعتبارسنجی (تکراری‌ها، کدملی نامعتبر، شماره تکراری) قبل از ثبت واقعی نمایش داده می‌شود.

### ج) نکات استقرار

- تغییر اسکیما (ستون‌های `firstName`/`lastName` کاربر) با همان `prisma db push` خودکار اعمال می‌شود؛ کاربران قدیمی بدون تغییر می‌مانند و فرم ویرایش، نام آن‌ها را از «نام و نام خانوادگی» قبلی تفکیک می‌کند.
- «حساب مدیر مدرسه» در جزئیات هر مدرسه هم با همین قواعد ساخته می‌شود (کدملی + رمز 123456)؛ ثبت مجدد همان کدملی، رمز را به پیش‌فرض بازمی‌گرداند.
- فرم ورود (`/login` و `/superadmin`) گزینه **«من ربات نیستم»** دارد؛ بدون تیک آن، ورود با رمز و درخواست کد پیامکی انجام نمی‌شود. این گزینه سمت مرورگر اعمال می‌شود و جای CAPTCHA سمت سرور را نمی‌گیرد؛ در صورت نیاز به حفاظت قوی‌تر، سرویس CAPTCHA در لایه Reverse Proxy اضافه کنید.

## ۱۴. اعلام شروع کلاس آنلاین (سوییچ معلم + پاپ‌آپ دانش‌آموز)

شروع کلاس آنلاین دو مرحله‌ای است تا هیچ اعلانی بدون استریم واقعی معلم ارسال نشود:

### الف) جریان معلم

- در بخش «کلاس آنلاین» هر معلم برای هر کلاس مجاز خود یک **سوییچ «شروع کلاس»** دارد. وضعیت سوییچ از جلسه واقعی در سرور خوانده می‌شود و با تازه‌سازی صفحه نمی‌پرد.
- روشن‌کردن سوییچ → دیالوگ پیکربندی (عنوان جلسه + گروه اطلاع‌رسانی) → جلسه ساخته می‌شود و معلم وارد اتاق می‌شود. **در این مرحله هنوز هیچ اعلانی ارسال نمی‌شود.**
- به‌محض ورود موفق معلم به اتاق و آماده‌شدن استریم او (دسترسی واقعی دوربین/میکروفون)، endpoint `POST /api/live-sessions/[id]/announce` فراخوانی می‌شود و اعلان شروع (پیام دعوت گروه + اعلان درون‌برنامه‌ای + پوش + پاپ‌آپ) یک‌بار برای همیشه ارسال می‌شود. اعلام با claim اتمیک `announcedAt` ضدتکرار قطعی دارد؛ فراخوانی تکراری/موازی هیچ اعلان دوباره‌ای نمی‌سازد.
- اگر دسترسی دوربین/میکروفون معلم رد شود یا استریم آماده نشود، جلسه خودکار پایان می‌یابد (سوییچ خاموش می‌شود)، خطای قابل فهم نمایش داده می‌شود و **هیچ اعلان شروعی برای دانش‌آموزان نمی‌رود**. سوییچ جایگزین مجوز مرورگر نیست.
- خاموش‌کردن سوییچ با تأیید معلم، جلسه و استریم را برای همه پایان می‌دهد (همان مسیر امن «پایان جلسه»).

### ب) قطع موقت اینترنت معلم

- قطع/خروج معلم میزبان پایان قطعی نیست: رویداد `live:host-status` وضعیت اتصال را به همه شرکت‌کنندگان می‌گوید و پس از **مهلت اتصال مجدد** (متغیر محیطی `LIVE_HOST_GRACE_SECONDS`، پیش‌فرض ۶۰ ثانیه؛ حداقل ۵) اگر معلم برنگردد، سرویس سوکت جلسه را در سرور پایان می‌دهد و وضعیت سوییچ/دعوت‌ها برای همه به‌روز می‌شود. بازگشت معلم در مهلت، تایمر را لغو می‌کند.

### ج) پاپ‌آپ دانش‌آموز «کلاس شما شروع شد!»

- فقط برای **دانش‌آموزان عضو همان کلاس** (رویداد `live:class-started` به اتاق‌های کاربری آن‌ها) و روی هر صفحه‌ای از برنامه نمایش داده می‌شود؛ شامل نام معلم، کلاس، عنوان جلسه، دکمه «ورود به کلاس» و «بعداً».
- هر شروع جلسه شناسه یکتا دارد؛ دریافت تکراری/اتصال مجدد پاپ‌آپ دوباره نمی‌سازد (ضدتکرار سمت سرور با `announcedAt` + سمت کلاینت با مجموعه شناسه‌ها). دانش‌آموزِ داخل همان جلسه پاپ‌آپ نمی‌گیرد؛ جلسه پایان‌یافته پاپ‌آپ نمی‌سازد و اگر هنگام نمایش پایان یابد، دکمه ورود غیرفعال و وضعیت «کلاس پایان یافته است» می‌شود. چند جلسه هم‌زمان به‌صورت صف عمودی نمایش داده می‌شوند.
- دانش‌آموزی که هنگام شروع آفلاین بوده، پس از اتصال مجدد سوکت جلسات فعال اعلام‌شده را از سرور می‌گیرد و دعوت معتبر نمایش داده می‌شود.
- «ورود به کلاس» وضعیت و مجوز را دوباره در سرور بررسی می‌کند؛ دوربین/میکروفون دانش‌آموز فقط با اقدام خود او و پیش‌فرض خاموش فعال می‌شود. «بعداً» پاپ‌آپ را می‌بندد؛ جلسه فعال همچنان در بخش کلاس آنلاین و پیام دعوت گروه در دسترس است.
- صدای هشدار کوتاه اختیاری است و در تنظیمات («صدای هشدار شروع کلاس») کنترل می‌شود؛ نمایش پاپ‌آپ به پخش صدا وابسته نیست و محدودیت پخش خودکار مرورگر رعایت می‌شود. انیمیشن‌ها ملایم و متناهی‌اند و تنظیم `prefers-reduced-motion` دستگاه رعایت می‌شود.
- هماهنگ با سیستم‌های موجود: برای صفحه فعال پاپ‌آپ، برای برنامه بسته/پس‌زمینه پوش (دسته `LIVE_SESSION_NEW` با همان کلید ضدتکرار)، و پیام دعوت خودکار در گروه — بدون هیچ اعلان موازی تکراری. همه گیت‌های دسترسی (اعلام فقط توسط میزبان، جلسه فعال، امکان onlineClass مدرسه) سمت سرور اعمال می‌شود.

## ۱۵. به‌روزرسانی نسخه جدید — بدون از دست رفتن داده

**تفکیک مسیرها:** استقرار اولیه = `scripts/deploy.sh`؛ به‌روزرسانی = `scripts/update.sh`. اگر stack موجود باشد، `deploy.sh` اجرای مجدد را رد و به `update.sh` راهنمایی می‌کند (`DANIAR_FORCE_DEPLOY=1` فقط با اطمینان).

```bash
bash scripts/update.sh
```

- آپدیت نیازی به آزادسازی پورت 3034 ندارد: اشغال پورت توسط پروکسیِ خود پروژه مانع نیست و کانتینرها درجا جایگزین می‌شوند؛ **هیچ سرویس دیگری روی میزبان لمس نمی‌شود**.
- «موفقیت» فقط پس از: پایان موفق سرویس migrate + healthy‌شدن همه سرویس‌های فعال اعلام می‌شود؛ در شکست، لاگ سرویس مشکل‌دار و راهنمای بازیابی چاپ می‌شود.

**داده‌های شما (مدارس، کلاس‌ها، گروه‌ها، کاربران، پیام‌ها، تکالیف و پیوست‌ها) روی ولوم `daniar_data` زندگی می‌کنند و آپدیت/بازسازی کانتینرها هرگز ولوم را حذف نمی‌کند.** زنجیره حفاظت در هر آپدیت، به‌ترتیب:

1. **پشتیبان کامل روی میزبان** — `scripts/backup.sh` (بکاپ آنلاین SQLite + tar آپلودها) در `./backups` ثبت می‌شود؛ اگر پشتیبان‌گیری شکست بخورد، ادامه با تأیید صریح شماست.
2. **شمارش داده‌های حیاتی پیش از آپدیت** — مدارس/کلاس‌ها/گروه‌ها/کاربران/پیام‌ها شمرده و نمایش داده می‌شوند.
3. **مهاجرت ایمن خودکار** — سرویس `migrate` با `prisma migrate deploy` (غیرمخرب) تغییرات اسکیمای نسخه جدید را اعمال می‌کند؛ سپر داخلی entrypoint **پیش از هرگونه تغییر دیتابیس** یک پشتیبان آنلاین در خود ولوم (`/data/backups/pre-migrate-…db`، نگهداری ۷ نسخه آخر) می‌سازد — حتی اگر بدون `update.sh` آپدیت کنید. اگر ساخت این پشتیبان ناموفق باشد (مثلاً دیسک پر)، مهاجرت عمداً متوقف می‌شود تا داده‌ها بی‌سپر تغییر نکنند. baseline دیتابیس‌های قدیمی هم فقط پس از **تأیید تطابق schema** با `prisma migrate diff` ثبت می‌شود؛ دیتابیس غیرمطابق = توقف با حفظ داده‌ها.
4. **راستی‌آزمایی پس از آپدیت** — شمارش‌ها دوباره گرفته و با قبل مقایسه می‌شوند؛ کاهش هر شمارنده خطای صریح با راهنمای بازیابی می‌دهد.

**چند هشدار مهم:**

- هرگز `docker compose down -v` اجرا نکنید — تنها دستوری است که ولوم `daniar_data` را حذف می‌کند. (`down` بدون `-v` و `up -d --build` بی‌خطرند.)
- برای گزارش سلامت داده در هر زمان: `bash scripts/verify-data.sh` (یکپارچگی + شمارش‌ها + فهرست پشتیبان‌های ولوم).
- راه‌های بازیابی در بدترین حالت: پشتیبان میزبان (`scripts/restore.sh`)، پشتیبان‌های داخل ولوم (`/data/backups`)، و نسخه پیشین خود دیتابیس (`/data/daniar.db.prev`).
- برای پشتیبان‌گیری دوره‌ای می‌توانید یک cron بسازید: `0 3 * * * cd /path/to/daniar && bash scripts/backup.sh ./backups >> backups/backup.log 2>&1`

## نکتهٔ مهم برای استقرار روی VPS (پیش‌نمایش dev با LiveKit Cloud)

محیط پیش‌نمایشِ سندباکس فعلاً با **LiveKit Cloud** کار می‌کند: `.env` سندباکس `NEXT_PUBLIC_LIVEKIT_WS_URL` و `LIVEKIT_INTERNAL_URL` را به پروژهٔ ابری اشاره می‌دهد و کلیدهای همان پروژه را دارد. این مقادیر **فقط** در `.env` سندباکس زندگی می‌کنند — نه در کد، Dockerfile، docker-compose، گیت یا بستهٔ استقرار (`.env` عمداً از مخزن و آرشیو حذف شده؛ روی سرور با `cp .env.example .env` از صفر ساخته می‌شود).

روی سرور تولید VPS هیچ‌کدام از این‌ها لازم نیست:

- `COMPOSE_PROFILES=media` (و در صورت نیاز `media,turn`) — LiveKit و coturn روی خود سرور بالا می‌آیند؛ استقرار کاملاً مستقل است و درگاه وب همان `127.0.0.1:3034` می‌ماند.
- اگر LiveKit Cloud یا سرور رسانهٔ جدا می‌خواهید، الگوی `.env.example` (بخش «سرور رسانه جدا / LiveKit Cloud») را ببینید؛ `LIVEKIT_INTERNAL_URL` با اسکیم `wss://` یا `https://` هر دو پذیرفته می‌شود.
- ⚠ با سرویس بیرونی/Cloud، متغیرهای TURN (`LIVE_TURN_*` و `LIVEKIT_PUBLIC_TURN_HOST/PORT`) را خالی بگذارید تا STUN/TURN خود آن سرویس (شامل TURN/TLS) اعمال شود؛ مقدار کهنه TURN خود Cloud را کنار می‌زند.
- متغیرهای «پل رسانهٔ عمومی پیش‌نمایش» قدیمی (LIVEKIT_PUBLIC_TURN_* و LIVE_TURN_* به رلهٔ آزمایشی 159.223.110.159:3478) فقط متعلق به حالت LiveKit محلیِ سندباکس بودند؛ در حالت Cloud کامنت‌اند و در تولید معنا ندارند — استقرار بدون آن‌ها کامل است.
